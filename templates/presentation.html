SYSTEM DESIGN • PATTERNS

Architecture: Strategy & Factory Patterns

Decoupled, extensible architecture separating orchestrator business logic from platform protocols.

🏛️ The Publisher Class Hierarchy

Unified abstraction layer defined in publisher/base.py:

class BasePublisher(ABC): # Abstract methods required by every platform @abstractmethod def validate_credentials(self) -> Dict[str, Any]: ... @abstractmethod def publish(self, content, media_paths, options) -> PublishResult: ... def is_configured(self) -> bool: ...
• Concrete Publishers: XPublisher, FacebookPublisher, InstagramPublisher, ThreadsPublisher, TikTokPublisher, and fallback _GenericPlatformPublisher.

🎛️ PublisherManager: The Central Dispatcher

Located in publisher/manager.py:

  • Factory Routing: create_publisher() normalizes platform strings (e.g. "x", "twitter" → "X (Twitter)").
  • Concurrent Dispatch: Dispatches common or customized copy to each account.
  • Audit Trail: Automatically records results in output/posts_history.json.
  • Draft & Schedule Lifecycle: Handles immediate dispatch, draft saving, and scheduled times.
New social channels can be plugged in by creating a subclass of BasePublisher with zero changes to existing network logic.
DATA CONTRACTS • AUDIT TRAIL

Standardized PublishResult & History Schema

Consistent output structures across all platforms for error isolation and full execution traceability.

📦 PublishResult Dataclass (publisher/base.py)

Every publisher returns this identical dataclass:

@dataclass class PublishResult: platform: str account_name: str success: bool post_id: Optional[str] = None post_url: Optional[str] = None message: str = "" simulated: bool = False timestamp: str = field(default_factory=...) raw_response: Optional[Dict[str, Any]] = None

Converts cleanly to JSON dictionary via result.to_dict().

PLATFORM PROTOCOL • X (TWITTER)

X (Twitter) Engine & Pure Python OAuth 1.0a

Zero external OAuth library bloat: hand-crafted RFC 3986 percent encoding & HMAC-SHA1 signer.

🔐 Pure-Python OAuth 1.0a (publisher/oauth_helper.py)

Cryptographic signing protocol:

# 1. Collect query + body + oauth params # 2. RFC 3986 percent-encode and sort lexicographically param_string = "&".join(f"{k}={v}" for k, v in sorted_encoded) # 3. Form Signature Base String base_string = f"{METHOD}&{rfc_quote(url)}&{rfc_quote(param_string)}" # 4. Generate HMAC-SHA1 digest using consumer_secret & token_secret key = f"{rfc_quote(secret)}&{rfc_quote(token_secret)}" hashed = hmac.new(key.encode(), base_string.encode(), hashlib.sha1) sig = base64.b64encode(hashed.digest()).decode() # 5. Build Authorization Header return f'OAuth oauth_consumer_key="...", oauth_signature="{sig}"...'

🚀 Two-Stage Publishing Flow

1. Character Boundary Enforcement
Strict 280-character ceiling checked before any network call.
2. Multipart Media Upload (v1.1 API)
POST https://upload.twitter.com/1.1/media/upload.json
Uploads binary image stream with OAuth 1.0a header → receives media_id_string.
3. Tweet Dispatch (v2 API)
POST https://api.twitter.com/2/tweets
JSON payload: {"text": content, "media": {"media_ids": [...]}}.
4. User Identity Validation
Live health check via GET /2/users/me confirms active handle.
PLATFORM PROTOCOL • META GRAPH V20.0

Facebook Pages & Instagram Business Flows

Integrating Meta Graph API v20.0 for direct page feed publishing and Instagram container flows.

📘 Facebook Pages Publisher

Uses Page Access Tokens with 63,206-character allowance:

With Media:
POST https://graph.facebook.com/v20.0/{page_id}/photos
Multipart stream containing binary image file + caption parameter.
Text-Only:
POST https://graph.facebook.com/v20.0/{page_id}/feed
Form body containing message and Page Access Token.
Validation:
GET /{page_id}?fields=id,name,link verifies page existence.

📸 Instagram Container Architecture

Enforces mandatory media and a two-phase publishing lifecycle:

Phase 1 • Create Media Container:
POST https://graph.facebook.com/v20.0/{ig_user_id}/media
Payload: image_url (publicly accessible URL) + caption (≤ 2,200 chars). Returns creation_id.
Phase 2 • Media Container Publish:
POST https://graph.facebook.com/v20.0/{ig_user_id}/media_publish
Payload: creation_id + Page Access Token.
Permalink Generation:
Resolves permalink to standard shortcode format /p/{shortcode}/.

ENGINEERING HIGHLIGHT • SANDBOX SIMULATOR

Dual-Mode Architecture: Sandbox vs Live

Zero-friction local development: auto-pivots to simulated execution when credentials are empty.

🧪 Simulation Sandbox Mode

No API Keys Needed

Triggered whenever is_configured() returns False:

  • Simulates realistic snowflake IDs (e.g. 1896694935599354582).
  • Generates valid-looking permalinks for IG (/p/TxN5r_DOzBH/) and Threads.
  • Verifies attached local file existence on disk via _verify_media_exists().
  • Appends full execution audit entry to output/posts_history.json with simulated: true.
  • Allows thorough UI & operational testing with zero danger of posting live spam.

🟢 Live Production Mode

Auto-Activates

Engages automatically when credentials exist in form or .env:

  • Signs real HTTP requests with HMAC-SHA1 OAuth 1.0a or Bearer authorization.
  • Performs multi-part file uploads to official Twitter/Meta/TikTok media CDNs.
  • Creates official containers and executes immediate live publishing.
  • Captures upstream HTTP errors (401 Bad Token, 403 Permissions, 429 Rate Limit).
  • Stores upstream post IDs and live URLs in the history audit log.

🛡️ Credential Security & Live Validation

Live Health Check (POST /api/connections/validate)
Directly queries upstream identity endpoints (e.g. api.twitter.com/2/users/me, graph.facebook.com/v20.0/{id}) to verify token validity before publishing.
Secret Masking (_mask_secret)
Secret keys longer than 6 characters display only the first 3 and last 3 characters (e.g. key...xyz) to prevent accidental shoulder-surfing leaks.
CRUD API
Full REST API support: GET /api/connections, POST /api/connections, and DELETE /api/connections/<name>.

EXTENSIBILITY • DEVELOPER GUIDE

How to Add a New Social Platform in 3 Steps

Clean architectural hooks allow plugging in LinkedIn, YouTube, or Bluesky in minutes.

1. Implement BasePublisher Subclass

class LinkedInPublisher(BasePublisher): def __init__(self, account_name, credentials=None): super().__init__("LinkedIn", account_name, credentials) self.access_token = self.credentials.get("access_token") def publish(self, content, media_paths=None, options=None): if not self.is_configured(): return PublishResult("LinkedIn", self.account_name, True, simulated=True) # Upstream REST call to /v2/ugcPosts ...

2. Register in PublisherManager

# publisher/manager.py def create_publisher(self, platform, account_name, credentials): norm = self.normalize_platform_name(platform) if norm == "LinkedIn": return LinkedInPublisher(account_name, credentials) ...

3. Add UI Pill & Limits

Add a <div class="channel-pill">LinkedIn</div> and a 3,000-character limit counter in templates/publish_work.html.
